## 1. 今回やったこと（本番反映済み）

### 1-1. 実測で見つかった最大の問題（改修前）
| 項目 | 改修前（実測） |
|---|---|
| トップページ1表示の転送量 | **71 MB**（画像182枚 63MB / フォント202リクエスト 5.2MB / JS 1.3MB gz） |
| 最大JSチャンク | **4,618,818 bytes**（data.ts＝全店舗＋全特集記事がブラウザに配信） |
| Lighthouse mobile Performance | 55（トップ）/ 52（店舗）/ 58（地域） |
| LCP（シミュレーション） | 49.1s / 34.7s / 37.1s |
| Search Console 28日 | クリック175 / 表示8,121 / CTR 2.15% / 平均11.6位、モバイル77% |

原因:
1. `'use client'` のコンポーネント13個が `@/lib/data`（10,791行＋特集ファイル群）を import → データ全体がクライアントバンドルに同梱
2. カード画像が CSS `background-image`（遅延読み込み不可）＋ Unsplash w=1600 / Wikimedia 1280px の原寸
3. Google Fonts を4ファミリー18ウェイトで読み込み（CSS 453KB、実際に使うのは12ウェイト）
4. `components/RegionsShowcase.tsx` に `'use client'` が無く、HomeClient 経由でクライアント化して `getRegionStats`（全店舗依存）を引き込んでいた（1回目の修正後も 4.6MB が残った真因）

### 1-2. 修正内容（63件の確定所見のうち実装分）
- **バンドル分割**: `lib/regions.ts`（型＋軽い定数）を分離。client component は `@/lib/regions` のみ import、データは server page から `RestaurantCardItem` / `SearchItem`（Pick型）で props 渡し
- **再発防止**: `postbuild` で `scripts/check-client-bundle.sh`（データ混入・1.5MB超チャンクでビルド失敗）。規約を CLAUDE.md に明記
- **画像**: 全カードを `<img loading="lazy" decoding="async">` に変更、`lib/imageUrl.ts` の `sized(url, 640)` で縮小URL生成。トップの background-image 183→0
- **フォント**: 使用ウェイトのみ（Shippori 5 / Noto Sans JP 4 / Zen Kaku 1 / JetBrains 2）、画像CDNへ preconnect
- **構造化データ**: 営業時間パーサーを `lib/openingHours.ts` に分離（連続曜日「日月」・「祝」・「・」区切り・「翌2:00」対応。対応率 255件中 247件＝96.9%）、`acceptsReservations` を boolean に、`geo`（GeoCoordinates）と `hasMap` を追加、Article の dateModified の偽装をやめる
- **URL・インデックス**: 特集記事の日本語IDを canonical / sitemap / JSON-LD で percent-encode に統一、sitemap の lastmod を DB の updated_at に（無い物は省略）、`force-dynamic` 撤去、robots の `host` 撤去、www と vercel.app を machinowa.tokyo へ 301、全公開ページに canonical、検索ページ noindex、削除済み特集の判定を日本語IDに対応、シーンのパンくずURL修正、meta description の「全国47都道府県」を実態に合わせて修正
- **IndexNow**: 廃止済みの Google/Bing sitemap ping を IndexNow（Bing/Yandex/Naver 等）に置換。key `162afc58bccd7cd84571c9e5637e3f74`
- **検索UX**: 業種セレクトと絞り込みロジックの不一致修正、NFKC＋カナ→かな正規化、タグ数を絞り込み結果ベースに
- **地域ハブ**: 特集が全国共通4本だったのを地域別に。ハードコードの地域数を動的に
- **モバイル**: `.section-head` の inline `gridTemplateColumns` が media query を潰していたのを除去、nav のタップ領域拡大
- **404/エラー**: `app/not-found.tsx` / `app/error.tsx` 追加、`<main>` ランドマーク、select/リンクの aria-label
- **API**: エラー詳細（DBメッセージ等）の外部露出を停止、revalidate の失敗パス返却
- **pre-commit**: 画像疎通チェックをステージ差分の新規URLのみに（Wikimedia 429 で全件検査が止まる問題）

## 2. SEO で伸ばすために必要な機能（優先順）

Search Console の実データ（流入の大半が**店舗名の指名検索**、店舗ページが表示の58%・平均9.3位、特集は16.6位、CTR 2%前後）に基づく。

### 優先度 A（流入に直結・実装コスト小）
1. **店舗ページの title / description テンプレ改善（CTR対策・最大の伸びしろ）**
   - 現状 title: `店名 | エリアの業種 — マチノワ`、description: `desc` をそのまま（長さ不揃い）
   - 提案 title: `店名｜エリア×業種 営業時間・定休日・地図 - マチノワ`（32文字目安、指名検索者が求める「営業時間/場所」を含める）
   - 提案 description: `【最寄り駅】の【業種】「店名」。desc の1文目。営業時間 ○○、定休日 ○○。` を110文字で切る（機械生成できる）
   - 対象: 表示≥50 で CTR<1% の `/restaurant/r223`（表示310）、`/restaurant/r103`、`/feature/new-shibuya-harajuku` から着手
2. **「近くの店」内部リンク（座標を使う）**: 店舗ページの関連店を「同地域4件」から「半径2km以内の近い順」に。地図と一体で回遊性・内部リンクの質が上がる。`lib/geo.ts` があるので実装は小さい
3. **店舗→特集の逆リンク**: その店が登場する特集記事を店舗ページに「この店が登場する読みもの」として表示（特集の平均16.6位を店舗ページの評価で押し上げる）
4. **rating の扱い**: JSON-LD の `aggregateRating` に食べログ由来の数値を載せているなら Google のガイドライン（自サイトで収集していない評価の構造化データ）違反リスク。出典明記＋構造化データからは外す方が安全

### 優先度 B（ハブページで非指名検索を取りに行く）
5. **業種×地域ハブ** `/region/[key]/[cuisine]`（例: 東京×ラーメン）: `CUISINE_GROUPS`（14群）×16地域のうち **店舗3件以上ある組み合わせだけ**生成（薄いページを作らない）。sitemap と地域ハブからリンク
6. **エリア／駅ハブ**: `area` は179種あるが84%が1店舗のみ → 今は作らない。3店舗以上のエリアだけ将来自動点灯
7. **シーン×地域**（デート×大阪 など）も同じ「3件以上」ルールで

### 優先度 C（品質・鮮度シグナル）
8. **最終更新日の表示**と `dateModified` の実値運用（DBの updated_at を表示に使う）
9. **残り性能**: フォントCSSがまだ 1.16MB（12ウェイト・1,239 @font-face）。Zen Kaku（1ウェイト）と JetBrains Mono（2ウェイト）をシステムフォント代替にすれば約1/4削減。トップのHTMLは全228カードを描画して8件だけ表示しているため 387KB → 表示地域だけサーバー描画すれば ~100KB
10. **未処理の既知課題（申し送り.md）**: 真っ黒画像30店舗、推測表現を含む記事50本、座標未解決28件（Maps URL 追加）

| ページ | Perf | LCP | TTI | TBT | A11y | Best Practices |

**解釈**: JS と画像は解決した。スコアが伸び悩む残りの支配要因は**フォント（トップ 202ファイル 5.2MB、店舗 63ファイル 1.4MB）**。日本語 Web フォントは unicode-range で ~120 分割され、「ファミリー×ウェイト（現在12通り）×ページ内の文字種」の分だけファイルが増える。シミュレーション値（slow 4G 想定）のため実ユーザーの体感は観測値（フォント完了 ~1.0s、JS完了 ~3.8s、無スロットル）に近いが、Google の CWV 評価にはフォント削減が必要。
- 選択肢A（デザイン維持・効果中）: Shippori Mincho を 400/700 の2ウェイト、Noto Sans JP を 400/500 の2ウェイトに統一 → ファイル数 約1/2
- 選択肢B（効果大・デザイン判断要）: 本文を Noto Sans JP から端末フォント（ヒラギノ/Noto CJK）に切替え、見出しの Shippori Mincho だけ Web フォント → ファイル数 約1/4
- いずれもデザイン判断のため未実施（ユーザー決定待ち）
