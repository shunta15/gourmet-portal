# 「こだわり条件で絞る」— 仕様（2026-10-05・オーナー承認済み「これ入れていいよ」）

## 何を作るか
グルメの「さがす」（`/search`、`app/search/page.tsx`・`components/SearchClient.tsx`）に、大手グルメサイトの「条件で探す」にあたる絞り込みを足す。
いまあるのはキーワード・地域・ジャンル・タグだけ。ここに「こだわり条件」（予算・営業時間帯・駅からの近さ・予約・席数・設備など）を足す。
**試作（公開スイッチ ON のときだけ）**。公開はしない。

## 絶対に守ること
1. 公開しない（`vercel`・`git push`・main への操作は禁止）。worktree `/Users/shunta/claude/gp-portal`（ブランチ `proto/portal`）にコミットするだけ。
2. **公開スイッチ OFF のとき `/search` の出力を1バイトも変えない**（`lib/portal/launch.ts`）。新しい部品・CSS・データは `portalLive` のときだけ読み込む（店ページの `ShopActions` と同じ作法。CSS は `.fc-` 接頭辞、`app/globals.css` は変えない）。
3. **推測しない**。条件の判定に使うのは、店データに書いてあることだけ。判定できない店は、その条件では「不明」として扱い、「はい」にも「いいえ」にもしない。
4. 星・点数・口コミ数は使わない・出さない。架空の値を作らない。
5. Supabase・スプレッドシートに書き込まない。`.env*` を表示しない。npm install しない。`npx` で未導入の道具を取りに行かない。
6. サブエージェント禁止。開発サーバーはポート 3242 だけ（止めるのは `lsof -ti tcp:3242 | xargs kill`）。`pkill` 禁止。
7. `lib/data.ts` などの巨大ファイルを全文 Read しない。`"use client"` から `@/lib/data` `@/lib/db/*` を import しない。実行時に `fs` で `public/` を読まない。
8. `AGENTS.md` を先に読む。`next dev` が `AGENTS.md` を書き換えたら `git checkout AGENTS.md` で戻す。

## 手順1: まず数える（実装より先。結果を `proto-portal/FILTERS-COVERAGE.md` に表で残す）
グルメの全店（`getPlaces('gourmet')` または `getAllRestaurants()`。DB＋コードの全店。件数を明記）について、下の条件ごとに
「判定できた店の数（はい＋いいえ）」「はいの数」「不明の数」「元の文字列の例を15件（判定結果つき）」を出す。

| 条件 | 判定の元 | 判定の決まり（この決まりは変えない。疑問があれば報告に書く） |
|---|---|---|
| 予算の帯 | `budget` の文字列 | 帯は 〜1,000円 / 〜3,000円 / 〜5,000円 / 〜10,000円 / 10,001円〜。帯は「書いてある上限」で決める（「〜¥1,000」→1,000、「¥3,000〜¥4,000」→4,000、「¥3,000〜」のように上限が無ければ下限）。昼と夜が分けて書いてあれば夜の値（夜が無ければ昼）。読み取れない表記・「要確認」は不明 |
| 昼に開いている | 営業時間（`lib/portal/openNow.ts` の `weekFromText` で週の予定にできた店だけ） | いずれかの曜日の 12:00 に営業 |
| 深夜まで | 同上 | いずれかの曜日で 23:30 以降も営業（日をまたぐ営業を含む） |
| 朝から | 同上 | いずれかの曜日の 8:00 に営業 |
| 日曜に開いている | 同上 | 日曜に営業時間帯がある |
| いま営業中 | 既存（`getOpenStatus`） | 既存のまま |
| 駅から徒歩5分以内 | `lib/stations/storeStations.json` の `stated`（店自身の記載）の `walkMin` | 5 以下。記載の無い店は不明 |
| ネット予約のリンクあり | `reservationUrl` | http(s) の URL がある |
| 席数 | `seats` の文字列 | 数字が読めた店だけ。「20席以上」「50席以上」 |
| 設備・特徴（個室／駐車場／テイクアウト／テラス／カウンター／禁煙／子連れ） | `tags`・`highlights`・`desc`・`body` | その語が**肯定の文脈**で書いてある店だけ「記載あり」。否定（「ありません」「なし」「不可」など）は拾わない。「いいえ」は作らない（書いていない＝不明） |

**条件を画面に出す基準（オーナーへの報告に使うので、勝手に変えない）**
- 予算・営業時間帯・駅徒歩・予約・席数: 判定できた店が **100店以上**、かつ「はい」が **10店以上**。
- 設備・特徴: 「記載あり」が **10店以上**、かつ、ヒットから無作為に **30件**（30件未満なら全件）を選んで元の文と見比べ、**誤りが0件**。
  1件でも誤り（否定文を拾った、別の意味だった等）があれば、拾い方を直して検査をやり直す。直しても0件にならない条件は出さない。
  検査した30件（店ID・拾った文・判定）を `FILTERS-COVERAGE.md` に残す。
- 基準に届かない条件は実装しない（表には「出さない・理由」を書く）。

## 手順2: 実装
- 判定はサーバー側で作る（新規 `lib/portal/facets.ts`。店ごとに `{ budgetBand, lunch, late, morning, sunday, walk5, reserve, seats20, seats50, has: [...] }`、不明は `null`）。
  クライアントには店ID＋判定結果の小さな表だけを渡す（店データ全体を二重に渡さない）。
- `/search`（ON のときだけ）に「こだわり条件」のパネルを足す。
  - 条件は押すと ON/OFF になるボタン（複数選べる。全部を満たす店に絞る）。予算は帯を1つ選ぶ。
  - 各ボタンに、**いまの他の絞り込みを掛けた状態で、その条件を足すと何店になるか**を数字で出す。0店になる条件は押せない見た目にする。
  - 結果の件数をすぐ更新。「条件をすべて外す」。
  - 条件を1つでも選んだら、結果の上に「条件が分かっている店だけを表示しています（不明の店は含みません）」と出す。
  - 結果の各店に、当てはまった条件を小さな札で添える（例「深夜まで」「個室の記載あり」）。設備・特徴の札は必ず「〜の記載あり」と書く。
  - URL と同期（例 `?budget=3000&f=late,walk5`。既存の `q`・`region`・`cuisine`・`tag` と併用できる。戻る・進む・再読み込みで状態が保たれる）。
    `/search` は既に `noindex, follow`・canonical `/search`。これは変えない（絞り込みURLを検索エンジンに載せない）。
  - モバイル: 条件は下から出るパネル（開閉できる。選択中の数をボタンに表示）。タップ領域 48px 以上。
  - 見た目は今のグルメ版（生成りの紙・墨・朱・明朝・細い罫）に合わせる。色と書体は `app/globals.css` の変数。キーボード操作・focus の輪・`prefers-reduced-motion`・コントラスト 4.5:1。
- グルメのトップ（ON のときの `/gourmet`）から `/search` への「こだわり条件でさがす」の入口を1つ足す。
- `proto-portal/LAUNCH.md` の付録に、この機能の1段落を足す（どこに何があるか、基準、数え直し方）。
